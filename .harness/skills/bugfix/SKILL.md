# 버그 수정

## 입력

증상 (재현 순서 · 화면 · 로그 · 서버 응답 · 기대 동작).

## 절차

1. **경로 판정**: Network · Token · 동시성 · DIContainer · 서버 계약에 걸치면 L (`planner` → 승인).
2. **브랜치**: `dev` 에서 `fix/<kebab-case>`. 이미 배포된 버전의 긴급 수정이면 사용자에게 hotfix 여부를 묻는다 (`cicd.md`).
3. **원인 찾기**: 증상에서 코드 경로를 따라가 원인 가설을 세운다. 가설은 코드 근거(`경로:줄`)와 함께 적는다.
4. **재현 테스트 (RED)**: 버그를 재현하는 실패 테스트를 쓴다 (`add_test_file.py` 로 등록). `./Scripts/test.sh <테스트클래스>` 로 **버그 때문에** 실패하는지 확인한다.
   - 화면 · 기기 · 외부 서비스에 묶여 테스트로 재현할 수 없으면 이유와 수동 확인 절차를 적고 넘어간다.
5. **수정 (GREEN)**: 원인만 고친다. 관련 없는 정리를 섞지 않는다. 재현 테스트 통과 확인.
6. **회귀**: `./Scripts/test.sh` 전체.
7. **재발 방지 판단**: 같은 실수가 다른 곳에서도 날 수 있으면 규칙 · 검증 추가를 사용자에게 제안한다 (직접 규칙을 바꾸지 않는다).
8. L 이면 `reviewer`.

## 출력 (보고)

- 증상 → 원인 (근거) → 수정 내용
- 재현 테스트 이름과 RED → GREEN 결과, 전체 회귀 결과
- 재현 테스트를 못 만든 경우 이유와 수동 확인 절차
- 재발 방지 제안 (없으면 "없음")

## 완료 조건

- 원인을 코드 근거로 설명했다.
- 재현 테스트가 수정 전 실패 · 수정 후 통과했다 (또는 못 만든 이유를 보고했다).
- 전체 테스트가 통과했다.
