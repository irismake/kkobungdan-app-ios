# 기능 구현 (TDD)

## 입력

사용자 요청. 있으면 디자인(Figma) · API 스펙 · 관련 화면.

## 절차

1. **경로 판정** (`core.md` "작업 경로 · 역할"). L 이면 `planner` 계획 → 사용자 승인. M 이면 계획을 3~5줄로 공유한다.
2. **브랜치**: 보호 브랜치(`dev` · `staging` · `main`)에 있으면 `dev` 에서 `feat/<kebab-case>` 를 만든다. 리팩토링은 `refactor/`.
3. **기존 구조 찾기**: 가장 비슷한 기존 기능을 찾아 같은 계층 · 이름 · 조립 방식을 따른다.
4. **RED**: 고정할 동작(UseCase · ViewModel 상태 전이 · 변환 · Repository 매핑 · 오류 분기)마다 실패하는 테스트를 쓴다.
   - 새 테스트 파일은 `python3 Scripts/harness/add_test_file.py <경로>` 로 타깃에 등록한다.
   - `./Scripts/test.sh <테스트클래스>` 로 **기대한 이유로** 실패하는지 확인한다 (컴파일 오류만으로 RED 를 끝내지 않는다).
   - 리팩토링은 반대로 시작한다: 지금 동작을 고정하는 테스트가 없으면 먼저 추가해 GREEN 에서 출발한다.
5. **GREEN**: 테스트를 통과시키는 최소 구현 → 같은 명령으로 통과 확인.
6. **REFACTOR**: 규칙(`api` · `swiftui` · `concurrency` 등)에 맞게 정리 → 다시 통과 확인.
7. **마무리 검증**: `Scripts/harness/verify.sh` — 규칙 · 코드 검사(계약 테스트 등록 · Logger · textStyle · 계층 · 프리뷰 · 테스트 등록 · Secret · 토큰 로깅) + SwiftFormat · SwiftLint. 위반은 고치거나 이유를 보고한다. 빌드 · 전체 테스트는 CI 머지 큐가 한다.
8. **L 이면 `reviewer`** 에게 요구사항 체크리스트와 기준 ref(`dev`)만 넘긴다. 지적을 반영하고, 반영하지 않은 것은 이유를 남긴다.

테스트로 고정할 동작이 없는 순수 레이아웃 변경은 4~6 을 생략할 수 있다. 생략했으면 보고에 적는다.

## 출력 (보고)

- 바꾼 파일과 이유 (계층별)
- 요구사항별 충족 여부
- 실행한 테스트: RED 확인 → GREEN 결과 (실행하지 않았으면 그렇다고). 전체 테스트는 CI 머지 큐에서 확인된다고 적는다
- 디자인과 기존 스타일 차이 · 사용자에게 물을 것

## 완료 조건

- 요구사항을 모두 충족했거나, 못 한 항목과 이유를 보고했다.
- 추가 · 수정한 테스트가 실제 실행 결과로 통과했고, `verify.sh` 를 통과했다.
- L 이면 reviewer 판정이 "통과" 이거나, 남은 지적과 미반영 이유를 보고했다.
- 커밋 · PR 은 사용자가 요청할 때 `pr` 스킬로 한다.
