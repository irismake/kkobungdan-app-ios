# 하네스 4단계 — 작업 워크플로 · TDD

## 스킬 (`.harness/skills/`, Claude · Codex 공용)

| 스킬 | 실행 조건 | 입력 | 출력 | 완료 조건 |
|---|---|---|---|---|
| `feature` | 기능 추가 · 변경 · 리팩토링 | 요청 (+ 디자인 · API 스펙) | 파일별 변경 이유, 요구사항 충족, RED → GREEN 결과 | 요구사항 충족(또는 사유), 테스트 실제 통과, L 이면 reviewer 통과 |
| `bugfix` | 버그 · 잘못된 동작 | 증상 · 재현 순서 · 로그 | 증상 → 원인(근거) → 수정, 재현 테스트 결과, 재발 방지 제안 | 재현 테스트 수정 전 실패 · 후 통과, `verify.sh` 통과 |
| `api-sync` | 서버 스펙 변경, 계약 테스트 실패 | 서버 변경 내용 | 스키마별 변경 표, 반영 내역, 계약 테스트 결과 | 계약 테스트 통과, lock 갱신은 사용자 확인 후 |
| `pr` | 사용자가 커밋 · PR 을 요청할 때만 | 작업 브랜치 | 커밋, 기존 형식의 PR 본문, PR URL | 의도한 변경만 커밋, "테스트" 란이 실제 결과와 일치, 머지 안 함 |

- 후보였던 요구사항 분석 · 기능 설계는 `planner`(3단계)와 `feature` 1단계로, 리팩토링 · 단위 테스트 작성은 `feature` 로, 코드 리뷰는 `reviewer` 로 합쳤다. 통합 테스트는 테스트 인프라가 없어 보류.
- `api-sync` 는 커밋 이력에서 가장 자주 반복된 작업("서버 계약 업데이트")이다.
- Claude: `.claude/skills` → `.harness/skills` 심볼릭 링크, 설명(description)으로 자동 선택된다. Codex: `AGENTS.md` "작업 절차" 표에서 해당 스킬 파일을 읽는다.

## TDD 를 실제로 돌리기 위해 바꾼 것

| 문제 | 변경 |
|---|---|
| `core.md` 가 "테스트를 스스로 돌리지 않는다" → TDD 와 충돌 | 스킬의 TDD 단계(RED · GREEN)에서는 요청 없이 해당 테스트 클래스만 실행. 빌드 · 전체 테스트는 로컬 검증에 넣지 않고 CI 머지 큐가 맡는다 (7단계에서 결정). 실행하지 않은 검증은 보고하지 않는다 |
| `Scripts/test.sh` 가 전체만 실행 → RED/GREEN 반복이 느림 | `./Scripts/test.sh <클래스>[/<메서드>]` 지원 (인자 없으면 기존과 같음) |
| 테스트 타깃이 폴더 동기화가 아님 → 새 테스트 파일이 등록 안 돼 **실행되지 않은 채 통과로 보이는** 함정 | `Scripts/harness/add_test_file.py` — 그룹(없으면 생성) · 파일 참조 · Sources 등록, 중복 실행 안전, `plutil -lint` 실패 시 되돌림 |
| RED 를 컴파일 오류로 끝내는 경우 | `testing.md`: RED 는 기대한 이유로 실패해야 한다 |
